# 学んだ原理を知識カードにする

AI は設計もコーディングもしてくれる。しかし完成物だけを受け取っていると
「なぜその仕組みで動くのか」を理解する機会は失われる。このスキルは、いま終わった作業から
**別の技術にも持ち出せる原理**だけを取り出し、再利用可能なカードとして残すためのもの。

作ったものの記録は残さない（それは git とコードの仕事）。

## 前提を読む

作業前に必ず両方読む:

- [references/vault.md](references/vault.md) — Vault の場所・構造・MOC
- [references/card-format.md](references/card-format.md) — カードの形式と下限品質

## 起動のされ方

- `/capture-knowledge` — 引数なし。直近の会話と diff がそのまま入力
- `/capture-knowledge <観点>` — 拾う範囲の指定（例: `トランザクション周りだけ`）
- 「今回の学びをカードにして」等の依頼文

引数は絞り込みのヒントとして使うだけで、無くても動く。

`--vault <path>` を付けると、その回だけ Vault の場所を上書きできる（vault.md の解決順を参照）。
残りの引数は観点として扱う。

## 手順

### 1. 候補を抽出する

直近の会話と `git diff`（必要なら `git log`）から、**学習価値のある原理**を拾う。

拾う: 仕組みの理由を説明した箇所 / 複数要素の因果をたどった箇所 /
他の概念との関係に言及した箇所 / 制約から選択を導いた箇所。

拾わない: 操作手順、API の使い方、プロジェクト固有の事実、
「根本メカニズム」と「構成要素と因果関係」が埋まらないもの。

**数を目的にしない**。1回の capture で 0〜3枚が普通。ゼロなら「今回は無し」と言って終える。

### 2. 重複を検査する（書き出す前に）

`knowledge/`（サブフォルダを含めて再帰的に）と `decisions/` を走査し、候補ごとに:

- **同名ファイル** — あれば別名を提案する（wikilink がファイル名解決なので、
  カテゴリが違っても重複は事故）
- **同テーマのカード** — あれば**新規作成せず、既存カードへの追記を提案**する

`summary` とファイル名への grep で足りる。ここを飛ばさないこと。

### 3. 採否を人間に聞く

候補を一覧で提示し、`AskUserQuestion` で **採否と confidence だけ**を決めてもらう。
本文の執筆は AI がやる。既存カードへの追記になるものは、その旨を選択肢に明示する。

**人間の手数は「候補にチェックを入れる」だけにすること。ここが重くなった時点でこの仕組みは死ぬ。**

### 4. 書き出す

採用したものを `knowledge/<カテゴリ>/`（再利用可能な原理）または
`decisions/`（一回性の判断記録）へ。

- カテゴリは主分野1つ。既存カテゴリ一覧を見て選び、新設は vault.md の条件を満たすときだけ。
  またがる分野は `tags` で表す
- 形式は card-format.md のとおり。`summary` は frontmatter にだけ、リンクは `[[...]]`
- `updated` は今日の日付
- confidence は人間が選んだ値。AI が `verified` を付けない
- decision を書いたら、そこから一般化できる部分を knowledge に昇格させ、相互に `[[...]]` を張る

### 5. MOC を用意する

該当分野の `MOC/<分野>.md` が無ければ、Dataview クエリ1つだけのノートを作る
（vault.md 参照）。一覧の中身を手で書かないこと。

### 6. 報告

作成／追記したファイルを、パスと1行要約で列挙する。コミットはしない
（Vault は別リポジトリ。ユーザーが明示的に頼んだときだけ）。
