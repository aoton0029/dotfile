# PRD.md の雛形

見出しは**9個で固定**。増やさない、減らさない。番号を振っているのは、後段のツールや
レビューで「PRD 第5章より」と引用できるようにするため。

各見出しの下の丸括弧は書き方の指示。**埋めたら括弧ごと消す**。
HTMLコメントではなく括弧書きにしているのは、コメント記法だと消し忘れて生成物に残るため。

---

```markdown
# PRD: <タイトル>

**作成日**: YYYY-MM-DD ／ **ステータス**: Draft ／ **種別**: <Q1の回答>

## 1. 概要

（3〜5行。ここだけ読んで何を作るのか分かること。1文目は「〜するための〇〇」の形で言い切る）

## 2. 背景と目的

（なぜ作るのか。Q3で選ばれた痛みを、現状こうなっているという具体描写として書く。
「効率が悪い」ではなく、実際に何が起きているかを書く）

## 3. ビジョンと成功指標

（完成後の世界が2〜3行。続けて、それをどう判定するかを箇条書きで2〜4個。
定量が取れなければ定性でよいが、「使いやすい」のような判定不能なものは書かない）

## 4. ターゲットユーザーとユーザーストーリー

（Q2の利用者像を1〜2行。続けてユーザーストーリーを2〜4本、次の形式で）

- `<ユーザー種別>` として `<やりたいこと>` したい。なぜなら `<理由>` だから。

## 5. 主要機能

### MVP（最初のバージョンに必ず入れる）

（3〜6個。各機能は「見出し的な一行 ＋ 1〜2行の説明」）

### フェーズ2以降

（今回は作らないが構想にあるもの。無ければこの小見出しごと省いてよい）

## 6. スコープ外

（今回やらないことを明示的に。「〜はやらない（理由）」の形で3〜5個。
ここが空のPRDは後で必ず揉めるので、思いつかなければユーザーに1問だけ聞く）

## 7. 構成

（技術スタック、データの持ち方、実行・配布形態。決まっている範囲だけを書く。
決まっていない部分をそれらしく埋めない——8章に回す）

## 8. 未確定事項

（インタビューで決まらなかったこと、打ち切った質問、書きながら気づいた穴。
なければ「現時点でなし」と書く）

- [ ] <項目> — <なぜ決まっていないか / 何が分かれば決まるか>

## 9. 関連文書

（既存のREADME・設計書・参考URLへの相対リンク。無ければ「なし」）
```

---

## 書くときの注意

- **1〜3章を厚くする**。下流ツールにはPRDの先頭200行しか読まないものがあり、
  人間のレビューでも最後まで読まれるとは限らない。判断に効く情報を前に置く。
- **5章と6章は必ずセットで埋まっている状態にする**。「作るもの」だけあって
  「作らないもの」が無いPRDは、読む人ごとに範囲の解釈がずれる。
- **8章を空にするために推測で埋めない**。未確定事項が並んでいるのは正常な初稿の姿。
