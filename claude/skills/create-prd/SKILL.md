# 頭の中の案をPRDに落とす

新規プロジェクトの構想は、本人の頭の中では完成しているのに、書き出そうとすると
「何から書けばいいか」で止まる。逆に、種別・利用者・解決したい痛みの3つさえ決まれば
残りはほぼ芋づるで出てくる。このスキルは、その3つを起点に短いインタビューをして、
人に見せられる粒度の一枚ものに変換するためのもの。

狙いはPRDの完成度ではなく、**曖昧な案を議論できる形にすること**。だから決まっていないことは決まっていないと書き残す。

## いつ使うか

入口は2つあり、入力の届き方が違う。どちらでも同じように動くこと。

- **`/create-prd <タイトルor概要>`** — 引数として渡ってくる（例: `dotfilesの同期状態を見るCLI`）
- **「〇〇のPRDを作って」「〇〇をするプロジェクトの要求仕様をまとめたい。機能は〜」**

どちらの経路でも情報がゼロのとき（`/create-prd` を裸で叩かれた等）に限り、
「何を作りたいか一言で」と聞くところから始める。

## 手順

### 1. 狙いを言い返して認識を合わせる

題材は、引数として渡ってくることも、依頼文の中に書かれているだけのこともある。
**どちらも同じ「入力」として扱う**。引数が空でも「何を作りたいですか」と聞き返さない——
自動で呼ばれた場合、ユーザーは既に依頼文に書いている。

読み取れたことを2〜3行で言い返す。「PowerShell/WSL 両方から使う想定の CLI ツールで、
複数マシン間の dotfiles の同期ズレを検出したい、という理解で進めます」のように。

これを先にやるのは、認識のズレをインタビュー前に潰すため。ズレたまま7問聞くと、
7問ぶん的外れな選択肢を並べることになる。

### 2. 既存文脈を軽く読む

カレントディレクトリに `README.md` / `CLAUDE.md` / `package.json` / `pyproject.toml` などが
あれば読む。本当にゼロからなのか、既存プロジェクトへの追加なのかで、聞くべきことが変わる
（既存があるなら技術スタックは聞かずに読み取れる）。

ここは調査に深入りしない。**1〜2ファイルまで**。PRD作成の前段でコードベース全体を
探索し始めると、ユーザーが答えを待つ時間ばかり延びる。

### 3. インタビューする

[references/interview.md](references/interview.md) に従う。質問設計の本体はそちらにある。

### 4. PRD.md を書く

[references/template.md](references/template.md) の雛形に回答を流し込み、`docs/PRD.md` に
書き出す。`docs/` が無ければ作る。

既に `docs/PRD.md` がある場合は、上書きせずに中身を読み、差分の方針（追記するのか、
別プロジェクトなので別名にするのか）を提示して確認を取る。

### 5. 要約して引き継ぐ

生成したパスと、`## 8. 未確定事項` に残った件数を伝える。

## やらないこと

- **設計・実装に踏み込まない**。PRDは「何を作るか」まで。クラス設計やAPIシグネチャや
  コード例を書き始めると一気に長くなり、しかも後で設計を変えたときに嘘が残る。
  「どう作るか」は設計フェーズの仕事。
- **決まっていないことを断定で書かない**。推測で埋めると、ユーザーが決めた事実と
  AIの推測が読み手に区別できなくなる。これはPRDとして一番まずい壊れ方なので、
  分からないものは `## 8. 未確定事項` に上げる。
- **見出しを増やさない**。雛形の9見出しから増減させない。長いPRDは読まれないし、
  下流ツール（tsumiki の `dev-plan` 等）はPRDの先頭200行しか読まないものがある。
  情報を足したくなったら、見出しを足すのではなく既存の章の中で密度を上げる。
- **質問を7問より多くしない**。初期構想段階で10問超は答える気力を奪う。
  足りない分はTBDで残せばよく、それはPRDの欠陥ではなく正しい状態。
