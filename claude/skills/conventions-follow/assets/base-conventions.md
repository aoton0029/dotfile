## 1. 層の責務と厚みの配分

原則は **入口は薄く、service を厚く、汎用処理は utils へ**。

入口を薄く保つのは、同じ処理を別の入口（画面 / API / バッチ / CLI）から呼べるようにするため。
入口に業務ロジックを書くと、二つ目の入口ができた瞬間にコピーが生まれ、
片方だけ直されたバグが残る。

| 層 | やること | やってはいけないこと |
|---|---|---|
| 入口（view / api / controller） | 認可の確認、入力の受け取りと検証、service 呼び出し、結果の描画・シリアライズ | DB クエリ、業務ルールの判断、複数 service にまたがる手続きの組み立て |
| service | 業務ルール、トランザクション境界、複数モデルをまたぐ操作、外部サービス連携 | HTTP / リクエストオブジェクト・テンプレートへの依存 |
| model | データ構造の定義、リレーション、単一レコードで完結する派生値 | 業務フローの実行、外部 I/O |
| utils | 業務を知らない汎用処理（日付整形、ハッシュ、文字列正規化、ファイル操作） | 業務用語に依存した処理、model / service の import |
| config | 環境ごとの設定値と読み込み | ロジック |

**依存の向き**: 入口 → service → model / utils。逆向き（service が入口を import する等）は禁止。
逆流させると、テストのたびに HTTP の器を用意する羽目になる。

## 3. 配置判断表

「この処理をどこに置くか」で迷ったときの対応表。迷いをここで固定して、毎回ぶれないようにする。

| 書こうとしている処理 | 置き場所 |
|---|---|
| 画面や API のルーティング、ステータスコードの決定 | 入口（view / api） |
| 入力値の形式チェック（必須・長さ・型） | フォーム / スキーマ定義 |
| 「この条件のときは登録できない」等の業務判断 | service |
| DB への保存・取得・更新・削除 | service（クエリ本体は model か repository） |
| 複数テーブルをまたぐ更新とロールバック | service（トランザクション境界） |
| 外部 API の呼び出し | service（クライアントの薄いラッパは utils でも可） |
| 日付整形・単位変換・文字列正規化など業務を知らない処理 | utils |
| 定数・閾値・環境ごとに変わる値 | config |
| 手動運用スクリプト、一度きりの移行処理 | scripts |

判断に迷う処理が出たら、**その処理が業務用語を知っている必要があるか**で切る。
知らなくてよいなら utils、知る必要があるなら service。

## 5. docstring・コメント規約

### docstring

**書式**（<言語> の docstring として書く）:

```
<DOCSTRING_TEMPLATE>
```

- 1行目は**タイトル**。体言止めか短い文で、この関数が何をするものかを一言で
- 空行を挟んで**概要**。何をするかではなく、**なぜ・どんな前提で**必要なのかを書く。
  処理の逐次説明はコードを読めば分かるので書かない
- `Args:` は引数ごとに「名前 (型): 意味」。単位や許容範囲があれば必ず書く
- `Returns:` は返り値の型と意味。返さない場合は省略してよい
- `Raises:` は呼び出し側が捕捉すべき例外だけ

**書く対象**: 公開関数・クラス・モジュール。内部ヘルパーで名前から自明なものは省略可。

### コメント

- **なぜそうしたか**を書く。何をしているかはコードで表す
- 直せる分かりにくさはコメントで補わず、命名か分割で直す
- コメントアウトしたコードは残さない（履歴は git にある）
- `TODO:` を残すときは、何が決まれば消せるのかまで書く

## 6. エラーハンドリングとログ

- 想定内の失敗（入力不正、権限なし、対象が存在しない）は、**service が意味のある例外を投げる**か
  結果オブジェクトで返し、入口がそれを利用者向けの表現に変換する。
  入口で `except Exception` の握りつぶしをしない
- 予期しない例外は、握りつぶさずログに残して上位へ投げる
- ログには利用者の特定に足る識別子（ID など）を入れ、**秘匿情報（パスワード、トークン、
  個人情報の生値）は入れない**
- ログレベル: `debug` 開発時の追跡 / `info` 業務上の節目 / `warning` 継続可能な異常 /
  `error` 処理が失敗した

## 7. テスト方針

| 層 | テストの当て方 |
|---|---|
| service | ここを厚く。業務ルールの分岐・境界値を単体テストで網羅する |
| 入口 | 正常系1本と、認可・検証で弾かれる系を数本。ロジックは service 側で試験済みのはず |
| utils | 入出力が明確なので単体テストが最も安い。境界値を丁寧に |
| model | リレーションと制約が効いているかを最小限 |

テストは `tests/` にソース構成と対応させて置く。
入口を薄く保っていれば service のテストだけで大半のリスクが取れる——それが薄くする実利。

## 8. セルフチェック

実装が終わったら、変更したファイルを実際に開いて1項目ずつ照合する。

- [ ] 追加したファイルは配置判断表どおりの場所にあるか
- [ ] 入口に DB クエリや業務判断が漏れていないか
- [ ] service が入口固有のオブジェクト（リクエスト等）に依存していないか
- [ ] 業務を知らない処理が service に埋もれていないか（utils へ出せないか）
- [ ] 同じ処理が既存のどこかに無いか（重複を作っていないか）
- [ ] 公開関数に規約どおりの docstring があるか（タイトル・概要・Args・Returns）
- [ ] 命名規約に沿っているか。関数名は動詞始まりか
- [ ] 例外を握りつぶしていないか。ログに秘匿情報が乗っていないか
- [ ] service の分岐にテストがあるか
- [ ] 規約に無い判断をしたなら、この規約に追記したか
