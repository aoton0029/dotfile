# 新しいスタック用の拡張を書く

`assets/base-conventions.md` はスタックを知らない骨格。実際のプロジェクトで役に立つのは、
そこにスタック固有の具体値が入ってから。この文書は、Flask 以外のスタック
（FastAPI / .NET / Node など）の拡張を足すときの型をまとめたもの。

手本は `assets/flask-conventions.md`。迷ったらそれと同じ構造にする。

## 置き場所と名前

`assets/<stack>-conventions.md`。`<stack>` は小文字のスタック名（`fastapi`, `dotnet`, `express`）。
名前を固定しておくと、SKILL.md の手順2 が機械的に該当ファイルを引ける。

## 書き方

拡張はベースを**置き換えるのではなく、節番号で対応させて上書き・追記する**。
ベース側の節番号をそのまま見出しに使い、変える節だけ書く。

必ず埋める節:

| 節 | 埋める内容 |
|---|---|
| 0. 技術スタック | 使うライブラリと、それぞれが担当する範囲・触ってよい層 |
| 2. ディレクトリ構成 | 実際のツリーと各ディレクトリの1行説明 |
| 3. 配置判断表 | ベースの表を、そのスタックの実ディレクトリ名で書き直す |
| 4. 命名規約 | ファイル・クラス・関数・テンプレート・テストの具体例つき |
| 5. docstring 規約 | その言語の標準書式に沿ったテンプレートと実例1本 |
| 9. スタック固有の決めごと | フレームワーク特有の落とし穴と DO/DON'T |
| セルフチェック追加分 | 9節の決めごとを機械的に照合できる形にしたもの |

ベースと変わらない節（エラー方針やテスト方針が同じなら）は書かない。
重複させると、片方だけ更新されて食い違う。

## 9節に何を書くか

ここが拡張の主役。基準は「**このフレームワークで放っておくと崩れる箇所**」。

- 入力をどこで検証するか（生のリクエストを直接読むのを禁じる根拠つきで）
- 画面/レスポンスの共通化の仕組み（テンプレート継承、レイアウト、共通レスポンス型）
- 入口を薄く保つための具体的な線引き
- 永続化とトランザクションの境界（どの層で commit するか）
- 認証・認可のライブラリが持ち込む文脈依存（`current_user` 的なもの）を
  どこで素の値に落とすか
- 設定・秘密値の置き場所

各項目は**理由を1〜2行添える**。「なぜ禁止か」が書いていない規約は、
不便になった瞬間に破られる。

## DO / DON'T の例

9節には、そのスタックの実コードで DO と DON'T を並べて載せる。
DON'T 側は「動くけれど後で困る」書き方にする——構文エラーのような明らかな誤りは
例として役に立たない。DON'T の下に、それが**いつ困るのか**を1行で書く
（例:「同じ処理を API から呼びたくなった瞬間に全部書き写すことになる」）。

## 追加したら

`conventions-init` スキルの `references/interview.md` にある「スタック」の選択肢に
1行足す。足し忘れると、拡張が存在するのにベースだけで規約が起こされる。
