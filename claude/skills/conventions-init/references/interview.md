# 質問バンク

`AskUserQuestion` に流す質問と選択肢のたたき台。**そのまま全部使うのではなく、
手順1で答えが分かった項目を落として、残りから3〜4問を選ぶ**。

選択肢の文面は状況に合わせて書き換えてよい。大事なのは
「第1選択肢をそのまま選び続ければ妥当な規約が出来上がる」状態にすること。
`（推奨）` を付けるのはその合図。

---

## ラウンド1: 骨格

### Q. スタック（手順1で判定できていれば聞かない）

header: `スタック`

- `Flask`（拡張サンプルあり） / `FastAPI` / `その他 Python` / `別スタック`

判定できたときは質問せず「requirements.txt から Flask 構成と判断しました」と述べる。

### Q. ディレクトリ構成

header: `構成`

- **拡張サンプルの構成をそのまま使う（推奨）** — 迷いが減り、他プロジェクトと揃う
- **既存の構成を規約として固定する** — 実態に合わせる。既存プロジェクトならこちらが妥当
- **これから決める（一緒に組み立てる）** — ツリーを提示して確認を取りながら作る

既存コードがある場合は2番目を第1選択肢にする。実態と違う構成を規約にすると、
初日から全ファイルが違反状態になり、規約が形骸化する。

### Q. 層の厚み配分

header: `層構成`

- **入口は薄く / service を厚く / 汎用は utils（推奨）** — 同じ処理を画面と API の
  両方から呼べる。テストも service に集中できる
- **2層（入口 + model）で十分** — 小規模・単一入口。service を挟むと空の中継が増える
- **repository を分ける（入口 / service / repository / model）** — DB 実装を差し替える
  見込みがある場合

### Q. 出力先

header: `配置先`

- **`docs/CONVENTIONS.md`（推奨）** — チームで共有でき、AI からも参照できる
- **`docs/CONVENTIONS.md` + `CLAUDE.md` にポインタ** — AI に確実に拾わせたい場合
- **`CLAUDE.md` に直接書く** — 個人プロジェクトで文書を分けたくない場合

## ラウンド2: 書き方

### Q. docstring 書式

header: `docstring`

- **日本語・Google スタイル（推奨）** — 1行タイトル → 空行 → 概要 → `Args:` / `Returns:` / `Raises:`
- **英語・Google スタイル** — OSS 公開や多国籍チーム向け
- **NumPy スタイル** — 科学計算系のライブラリと揃える場合
- **型注釈のみ、docstring は公開 API だけ** — 内部ツールで記述コストを抑えたい場合

既存コードに書式があればそれを第1選択肢にする。途中で書式を変えると、
混在した状態が一番読みにくい。

### Q. 命名規約の厳しさ

header: `命名`

- **役割サフィックスを必須にする（推奨）** — `user_service.py` `UserRegisterForm` のように
  ファイル名・クラス名で層が分かる。grep で辿れるのが利点
- **言語の標準慣習のみ** — snake_case / PascalCase だけ決めて、あとは自由
- **既存コードの実態を追認する** — 手順1で読み取った命名をそのまま規約にする

### Q. エラーハンドリングとログ

header: `エラー`

- **service が専用例外を投げ、入口が表示に変換（推奨）** — 業務的な失敗と想定外の失敗を
  分けられる。入口ごとに表現（HTML / JSON）を変えられる
- **戻り値で成否を返す** — 例外を制御フローに使いたくない場合
- **今は決めない（TBD）** — 後から `/docs-resolve` で詰める

ログの秘匿情報禁止（パスワード・トークン・個人情報の生値）はベース既定として、
質問せずそのまま入れてよい。外す理由がまず無い。

### Q. テスト方針

header: `テスト`

- **service を厚く、入口は正常系＋認可のみ（推奨）** — 入口を薄く保つ設計と対で効く
- **全層に単体テスト** — 品質要求が高い、または長期保守が確定している場合
- **今は書かない（方針だけ残す）** — 個人ツールや検証段階

---

## 聞かないこと

以下はベースの既定をそのまま採用し、質問しない。選択肢を出しても
ほぼ全員が同じ答えを選ぶので、往復を増やすだけになる。

- 依存の向き（入口 → service → model / utils、逆流禁止）
- コメントアウトしたコードを残さない
- ログに秘匿情報を載せない
- 設定の秘密値をソースに直書きしない
- `TODO:` には「何が決まれば消せるか」まで書く

ただし規約ファイルにはこれらも**明記する**。質問しないことと、書かないことは別。
