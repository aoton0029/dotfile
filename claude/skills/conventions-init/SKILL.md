# 規約ファイルを対話で起こす

規約は、白紙から書かせると一般論の羅列になり、全部書き切ろうとして長くなり、
結果として誰も読まなくなる。逆に決めごとを1つずつ選ばせれば、
**選んだ本人が中身を覚えている規約**ができる。

このスキルの仕事は文章を捻り出すことではなく、**選択肢を出して決めさせ、
決まったものだけをテンプレートに流し込む**こと。決まらなかったものは `TBD` で残す。

## 入力

- `/conventions-init <タイトル/概要>` — 引数がプロジェクト名や一言説明になる
  （例: `/conventions-init 社内備品管理 Web アプリ`）
- 「〇〇の規約を作って」と依頼文の中に書かれているだけのこともある

**引数と依頼文はどちらも同じ「入力」として扱う**。引数が空でも即座に聞き返さず、
まず手順1のリポジトリ調査をする。そこから読み取れることの方が多い。
本当に何も分からないときだけ「何のプロジェクトですか」と一言聞く。

## 手順

### 1. まずリポジトリを見る

質問する前に、答えが既にある項目を潰しておく。聞かなくて済む質問を聞くと、
利用者は「このAI何も見てないな」と感じて以降の回答が雑になる。

読むもの:

- 依存ファイル（`requirements.txt` / `pyproject.toml` / `package.json` / `*.csproj`）→ スタック判定
- 既存のディレクトリツリー（深さ2程度）→ 実際の構成
- 既存コードの数ファイル → 命名の実態、docstring の有無と書式
- `CLAUDE.md` / `README.md` / `docs/` → 既に書かれている決めごと
- 既に `docs/CONVENTIONS.md` があれば読む。ある場合は新規作成せず、
  「既にあります。作り直しますか、不足分を足しますか」と確認してから進む

読み取った内容を3行程度で言い返してから質問に入る。
「Flask + SQLAlchemy 構成、app/ 配下に views と models はあるが services が無い、
docstring はほぼ無し、という状態から始めます」のように。

### 2. テンプレートを読み込む

土台は `conventions-follow` スキルに同梱されているものを使う（重複管理を避けるため、
このスキルはテンプレートを自前で持たない）。

- ベース: `../conventions-follow/assets/base-conventions.md`（このスキルのディレクトリからの相対）
- スタック拡張: `../conventions-follow/assets/<stack>-conventions.md`（例: `flask-conventions.md`）

見つからなければ `~/.claude/skills/conventions-follow/assets/` を直接見る。
それでも無ければベース無しで進めず、ユーザーに伝えて止まる。
テンプレート無しで生成すると、このスキルの意味である「既存の型に揃える」が失われる。

### 3. AskUserQuestion で決めごとを取る

質問は `references/interview.md` の質問バンクから選ぶ。詳しい選択肢の文面はそこにある。

進め方:

- **1回の呼び出しに3〜4問**まとめ、**2ラウンドで終える**のを目安にする。
  1問ずつ往復すると規約1本作るのに10往復かかり、途中で飽きられる
- 手順1で答えが分かった項目は**質問しない**。代わりに「〜と判断しました」と地の文で述べ、
  違えば言ってもらう
- 各質問の第1選択肢は、手順1の実態かベーステンプレートの既定に合わせ、
  ラベル末尾に `（推奨）` を付ける。全部そのまま選べば妥当な規約が出来上がる状態にする
- スタック拡張が存在するスタック（Flask など）なら、
  「拡張サンプルの決めごとをそのまま採用するか」を1問にまとめてよい。
  細部を個別に聞き直す価値は薄い

**ラウンド1（骨格）**: スタック確定 / ディレクトリ構成 / 層の厚み配分 / 出力先
**ラウンド2（書き方）**: docstring 書式 / 命名規約 / エラーとログ / テスト方針

ラウンド1の回答次第でラウンド2の選択肢を変える。例えば構成を「既存実態に合わせる」と
選ばれたら、命名規約の第1選択肢は既存コードから読み取った実態にする。

### 4. 書き出す

ベースの節構成（1〜9節）をそのまま使い、回答で穴を埋める。

- スタック拡張を採用した場合は、**節番号を対応させて上書き・追記する**。
  ベースの一般論と拡張の具体値を両方残さない（食い違いの元になる）
- 冒頭にタイトル（引数のプロジェクト名）と、1〜2行の概要を置く
- ツリーやテーブルのプレースホルダ（`<TREE>` `<DIR>` `<規約>` 等）を残さない。
  埋められない項目は `TBD（<何が決まれば埋まるか>）` と書く。
  空欄のまま残すと、後で見た人が「決まっているのに書き忘れた」のか
  「決まっていない」のか区別できない
- セルフチェック節は、この規約で実際に決めた項目だけに絞る。
  決めていないことをチェック項目に残しても照合できない

出力先は既定で `docs/CONVENTIONS.md`。無ければ `docs/` ごと作る。

### 5. 引き渡す

書き出したら:

- 決めた項目と `TBD` で残した項目を、それぞれ数行で報告する
- `CLAUDE.md` があれば、規約へのポインタを2〜3行足すことを提案する
  （実体は `docs/` に置き、`CLAUDE.md` からは参照だけ——二重管理を避けるため）
- 以降の実装では `conventions-follow` がこのファイルを読んで従うことを伝える
- `TBD` が残っているなら `/docs-resolve` で詰められることを添える

## 関連スキル

- `conventions-follow` — できあがった規約に従って実装させる側。テンプレートの本体も持つ
- `docs-prd` — 何を作るかがまだ固まっていないなら、規約より先にこちら
- `docs-resolve` — 規約に残した `TBD` を後から詰める
