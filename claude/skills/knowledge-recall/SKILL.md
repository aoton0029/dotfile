# 蓄積した原理を引き出す

貯めた原理が次の学習や設計に結び付くのはこのスキルのおかげ。
ここが動かないなら知識リポジトリを作る意味がない。

## 前提を読む

- [../capture-knowledge/references/vault.md](../capture-knowledge/references/vault.md) — Vault の場所と構造
- カード形式は [../capture-knowledge/references/card-format.md](../capture-knowledge/references/card-format.md)

## 手順

### 1. テーマを受け取る

`/recall-knowledge <テーマ>` の引数、または依頼文中の記述。どちらも同じ入力として扱う。
情報がゼロのときだけ「これから何をやりますか」と聞く。

`--vault <path>` を付けると、その回だけ Vault の場所を上書きできる（vault.md の解決順を参照）。
残りの引数はテーマとして扱う。

テーマから**検索語を広げる**（同義語、上位概念、隣接分野。例:「リトライ設計」なら
冪等性・exactly-once・バックオフ・分散トランザクション）。

### 2. frontmatter を直接読んで検索する

**Dataview クエリには依存しない**（AI 側では実行できない）。

`knowledge/`（サブフォルダを含めて再帰的に）と `decisions/` に対し、
**`tags` / `summary` への grep とファイル名マッチ**で始める。
カテゴリのフォルダで検索範囲を絞らないこと（またがる分野はタグ側にしか出ない）。
これで足りる。カードが約200枚を超える、あるいは全件走査が実用に合わなくなった時点で
MOC を入口にした段階検索への切り替えを検討する。それまでは仕組みを増やさない。

### 3. 1段だけ辿る

ヒットしたカードの `[[...]]` リンクと、そのカードを参照している側（バックリンク＝
カード名で grep）を **1段だけ**辿り、芋づるで関連を拾う。2段以上は辿らない（ノイズになる）。

### 4. 提示する

ヒットごとに:

- ノート名と `summary`
- **「根本メカニズム」と「構成要素と因果関係」の要点** — 今回の理解や設計の土台になるのはここ。
  この2節は要約せず、内容が伝わる密度で出す
- 今回のテーマとの接点（なぜこれが効くのか）を1行

**`confidence: hearsay` のカードは「未検証」と明示して出す。** `reasoned` も未検証である旨を添える。
カードの内容を、検証済みの事実のように扱って設計判断の根拠にしないこと。

ヒットが無ければ「該当なし」と言う。無理に遠いカードを差し込まない。

### 5. 締め

最後に、今回のテーマで**カードが欠けている領域**があれば1〜2行で指摘する
（作業後の `capture-knowledge` の的になる）。カードの作成はしない。
