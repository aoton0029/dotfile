# 図で語る設計書を書く

構造・流れ・状態・関係の説明には必ず図を置く。文章だけで済ませてよいのは、
判断の理由とトレードオフだけ。

## 手順

### 1. 対象と入力を確認する

- **これから作る** — `docs/PRD.md` があれば読む。無ければ依頼文から要件を読み取り、
  2〜3行で言い返して認識を合わせる。
- **既存コードから起こす** — エントリポイントから主要な呼び出し経路を追う。
  網羅的に読まず、図に描ける粒度が見えたら止める。

`docs/CONVENTIONS.md` があれば読み、その構成ルールに従う。

### 2. 図の構成を先に決める

本文を書く前に、章立てと各章に置く図の種類を宣言する。選び方は
[references/diagram-guide.md](references/diagram-guide.md)。

次の3つは常に検討する（不要なら理由を1行）。

| 図 | 答える問い |
| --- | --- |
| 構成図 | 何がいくつあり、どう繋がっているか |
| シーケンス図 | 誰がどの順に何を呼ぶか |
| フロー図 | 分岐と失敗経路を含め、処理はどう進むか |

永続データがあれば ER 図、寿命のあるオブジェクトがあれば状態遷移図を足す。

### 3. 図を先に描く

章ごとに **図 → 読み方3行以内 → 補足文** の順。逆順にすると図が文章の要約に堕ちる。
すべて Mermaid で書く。記法と落とし穴は diagram-guide.md。

### 4. 書き出す

[references/template.md](references/template.md) に従い `docs/DESIGN.md`
（機能単位なら `docs/design/<機能名>.md`）へ。既存ファイルがあれば上書きせず、
読んだうえで追記か別ファイルかを確認する。

### 5. 検算して引き継ぐ

- 構造・流れ・状態を説明する段落に、対応する図があるか
- 図の名前と本文の名前が食い違っていないか（最頻の壊れ方）
- シーケンス図に失敗経路が1本はあるか
- 未確定を断定で書いていないか

生成パスと未確定事項の件数を伝える。1件以上あれば docs-resolve を案内する。

## やらないこと

- **図のない設計書を出さない**。図を描けない＝構造が未確定なので、未確定事項に上げる。
- **1枚に詰め込まない**。ノード15個を超えたらレイヤ・ユースケースで割る。
- **コードを貼らない**。型定義とシグネチャは可、関数の中身は不可。
- **推測で断定しない**。確認していない挙動を図にするなら「未確認」と明記する。
  図は文章より信じられるぶん、嘘の害が大きい。
