# 単体リポジトリ ブランチ戦略 設計案

単一のリポジトリで完結する開発（アプリケーション、ライブラリ、CLI ツール、
設定リポジトリなど）を対象に、**作業ブランチの開始から `main` へのマージまで**の
運用モデルを定義する。

**本書はブランチ運用と文書運用の正本**である。ブランチ種別・命名規則・
文書メタデータ・文書種別の責務・設計 PR の必須項目は本書で定義し、
他の戦略文書はこれを参照・拡張する。

`main` マージ以降（タグ発行・成果物公開）は
[単体リポジトリ リリース戦略](solo-repo-release-strategy.md) を参照する。

複数リポジトリを協調させる開発は、本書を前提に差分のみを定義した
[マイクロサービス ブランチ戦略](microservice-branch-strategy.md) を参照する。

```yaml
status: proposed
implementation: planned
last_reviewed: 2026-08-17
```

---

## 1. 目的と対象

- `main` を常に説明可能で、再現可能な状態に保つ。
- コードと文書の乖離を防ぐ。
- 開発中に生まれる大量の作業文書で `main` を汚さない。
- 人間と AI エージェントが同じチェックポイントに従う。
- 個人・小規模でも維持できる最小限のプロセスにする。

対象:

- 単一リポジトリで完結する開発。
- リポジトリ種別は問わない（アプリ / ライブラリ / ツール / dotfiles / 文書リポジトリ）。

対象外:

- 常設の `develop`、`staging`、`release/*` ブランチ。
- Git ブランチを環境そのものとして扱う運用。
- 複数リポジトリにまたがる契約変更の調整（マイクロサービス版の責務）。
- タグ発行、成果物公開（リリース戦略側の責務）。

---

## 2. ブランチモデル

常設ブランチは `main` のみ。短命な作業ブランチを `main` から作り、
Pull Request 経由で戻す。

```text
main
  ├── feat/<topic>
  ├── fix/<topic>
  ├── docs/<topic>
  ├── design/<topic>
  └── chore/<topic>
```

### 2.1 ブランチ種別（正本）

| 接頭辞 | 用途 |
|---|---|
| `feat/` | 利用者または運用者に見える機能追加 |
| `fix/` | 不具合修正 |
| `docs/` | 振る舞いを変えない文書のみの変更 |
| `design/` | 実装に先行する大きな設計変更 |
| `chore/` | 依存関係、CI、開発環境、整理 |
| `hotfix/` | 稼働障害への緊急修正。通常の `fix/` より優先する場合のみ |

`hotfix/` の作成条件とその後の手順はリリース戦略側で定義する。

### 2.2 命名規則（正本）

- 小文字の kebab-case を使う。
- チケット番号がある場合は `feat/123-media-timeline` のように含める。
- 実装方法ではなく目的を表す。
- `update`、`work`、`temp` など内容が判別できない名前を避ける。

### 2.3 単体リポジトリでの適用

- リポジトリ横断のブランチ名合わせや先行マージは発生しない。
- `design/` は「設計書自体を正本として先にマージしたい場合」に限って使う（4.5 節）。
  それ以外の設計作業は `feat/` の中で作業文書として進める。

---

## 3. 作業サイクル

### 3.1 作業開始

1. 変更目的を 1 文で言えるまで絞る。
2. `git status` で未コミット変更と現在のブランチを確認する。
3. リモートの `main` を取得する。
4. 最新 `main` から作業ブランチを作る。
5. 変更が複数の独立した目的を含む場合はブランチを分割する。
6. 作業文書が必要な規模なら `.work/<topic>/` を用意する（4.2 節）。

既存の未コミット変更は、所有者と目的を確認せず移動、破棄、取り込みしない。

### 3.2 作業中

- 1 ブランチを 1 目的に限定する。
- 原則として数時間から 3 日程度でマージ可能な大きさにする。
- 大きな機能は後方互換な小変更へ分割する。
- コミットはレビュー可能な単位にする。
- コミットメッセージと PR タイトルは Conventional Commits に寄せる。
- 検討・調査・計画は `.work/<topic>/` に書き、`docs/` の正本には触らない。

### 3.3 作業完了

1. 作業文書を正本へ蒸留する（4.3 節）。
2. `.work/<topic>/` を削除する。
3. 検証を実行する（6 章）。
4. PR を作成し、文書影響欄を埋める（4.7 節）。
5. マージ条件（5 章）を満たしたら squash merge する。
6. 作業ブランチを削除する。

原則として squash merge を使い、`main` の 1 コミットを 1 変更目的に対応させる。

## 4. ドキュメント戦略（正本）

本章が本書の中核であり、**全リポジトリにおける文書運用の正本**とする。
マイクロサービス構成での追加分は
[マイクロサービス ブランチ戦略 4 章](microservice-branch-strategy.md) が差分として定義する。

### 4.1 正本と作業文書の分離

`main` に置くのは**正本のみ**とする。正本とは「その時点で承認されている、
今後も参照される情報」を指す。開発中に生まれる過程の文書は `main` に持ち込まない。

| 区分 | 例 | 置き場所 | `main` へマージ |
|---|---|---|---|
| 正本 | 設計書、ADR、API・契約、README、運用手順、ランブック、トラブルシューティング | `docs/`、リポジトリルート | する |
| 作業文書 | 機能設計書、実装計画、タスク分解、調査メモ、検討ログ、進捗表 | `.work/<topic>/` | **しない** |

理由:

- 正本と過程が混在すると、読み手がどれを信じてよいか判断できなくなる。
- 実装計画や進捗表はマージ時点で役目を終えるが、放置されると陳腐化した情報として残る。
- `main` の文書量が増えるほど、更新漏れと矛盾が発生しやすくなる。

#### 文書種別と責務（正本）

| 文書 | 答える問い | 更新契機 |
|---|---|---|
| PRD | なぜ作るか、誰の何を解決するか | 要件変更 |
| 設計書 | どう分割・実現するか | 設計変更 |
| API・契約 | 外部との境界で何を約束するか | I/F 変更 |
| ADR | なぜその選択をしたか | 重要な意思決定 |
| README | どこから読み、どう利用するか | 入口・利用方法変更 |
| 運用手順 | 日常的にどう操作するか | 運用変更 |
| ランブック | 構築・障害時に何をどの順で実行するか | 実機検証 |
| トラブルシューティング | 何が起き、どう診断・解決したか | 障害解決後 |

設計書は現在の採用設計を示し、ADR は選択理由を示す。
ADR の過去の決定を書き換えず、変更時は新しい ADR から旧 ADR を置き換える。

### 4.2 作業文書の置き方

作業文書は `.work/<topic>/` に置き、**Git で追跡する**。

```text
.work/
└── <topic>/
    ├── feature-design.md   # 機能設計書
    ├── impl-plan.md        # 実装計画・タスク分解
    └── notes.md            # 調査メモ
```

- `<topic>` は作業ブランチ名の topic 部分と揃える。
- `.gitignore` には**入れない**。理由:
  - 別マシン・別環境から作業を再開したときに内容が失われる。
  - AI エージェントと人が同じ内容を参照できなくなる。
  - PR のレビューで設計意図を提示できなくなる。
- 追跡した上で、マージ前に削除コミットを積むことで `main` に残さない。
- 秘密情報は `.work/` にも書かない。追跡対象であり履歴に残る。

`.work/` を複数ブランチで同時に持つ場合、topic ディレクトリが分かれていれば
競合しない。同じ topic を複数ブランチで扱わない。

### 4.3 蒸留（distill）手順

マージ前に、作業文書から正本への変換を必ず行う。

1. **昇格**: 作業文書のうち、今後も参照される決定を正本へ反映する。

   | 作業文書の内容 | 反映先（正本） |
   |---|---|
   | 採用した設計・構造 | 設計書 |
   | 選択理由・却下した代替案 | ADR |
   | 外部から見える I/F の変更 | API・契約仕様 |
   | 使い方・入口の変更 | README |
   | 日常操作・手順の変更 | 運用手順 |
   | 障害の診断・解決方法 | トラブルシューティング |

2. **破棄**: その変更限りの情報は正本に書かない。
   実装順序、進捗、担当、暫定的な調査結果、検討途中の案。
3. **要点の退避**: 削除前に、作業文書の要点（背景・採用案・却下案）を PR 本文へ転記する。
   経緯の履歴は PR と squash コミットに残る。
4. **削除**: `.work/<topic>/` を削除するコミットを積む。

蒸留を後回しにして「あとで書く」としない。作業文書を消した時点で内容は失われる。

### 4.4 蒸留判定の指針

判断に迷う場合の基準: **6 か月後の自分が読んで意味があるか**。

| 昇格させる | 破棄してよい |
|---|---|
| なぜその設計にしたか | どういう順で実装したか |
| 外部から見える振る舞い・制約 | 内部の作業分割 |
| 運用者が実行する手順 | 検証中に試して捨てた手順 |
| 既知の制限・未対応事項 | 作業中の TODO の消化状況 |
| 再現した不具合の条件と原因 | 調査中に立てて外れた仮説 |

「昇格させるべきものが 1 つもない」場合、`.work/` を作る規模ではなかった可能性が高い。
次回は作業文書なしで進める判断材料にする。

### 4.5 大規模設計の例外

設計そのものが成果物であり、実装前に合意が必要な場合は `design/<topic>` を使う。

```text
design/<topic>   → 設計書（正本）を docs/ に追加して先行マージ
   ↓
feat/<topic>     → 実装。実装計画は .work/ に置き、マージ前に破棄
```

- 先行マージする設計書には未実装であることを明記する
  （`implementation: planned`）。
- 実装完了時に `implementation` を更新する（リリース戦略 5 章）。
- この場合も実装計画・タスク分解は `.work/` 扱いで `main` に残さない。

#### 設計 PR の必須項目（正本）

- 背景と解決する問題。
- スコープと非スコープ。
- 採用案。
- 検討して却下した代替案。
- セキュリティ、可用性、データへの影響。
- 移行方法。
- ロールバックまたは撤退方法。
- 影響する範囲と文書。
- 未決事項。
- 実装の完了条件。

設計を先行させる条件:

- DB スキーマやデータ形式が変わる。
- 認証、ストレージ、外部依存の構成が変わる。
- ロールバックが難しい。
- 複数案の比較と明示的な決定が必要である。

### 4.6 文書メタデータ（正本）

`main` には、現在承認されている情報を置く。
承認済みの将来設計も置けるが、未実装であることを明記する。
設計の承認状態（`status`）と実装状態（`implementation`）を分離する。

```yaml
status: accepted
implementation: planned
last_reviewed: YYYY-MM-DD
```

`status`:

| 値 | 意味 |
|---|---|
| `draft` | 作成中。合意対象として未完成 |
| `proposed` | レビュー可能な提案 |
| `accepted` | 採用済みの決定または設計 |
| `superseded` | 後続の文書に置き換えられた |
| `rejected` | 検討したが採用しなかった |

`implementation`:

| 値 | 意味 |
|---|---|
| `not-applicable` | 実装状態を持たない方針・記録 |
| `planned` | 実装前 |
| `in-progress` | 実装中 |
| `partially-implemented` | 一部のみ実装済み |
| `implemented` | 設計に対応する実装・運用が存在する |

`last_reviewed` は、内容を最後に読み直して妥当性を確認した日付（`YYYY-MM-DD`）。

置き換えられた文書は削除せず、必要に応じて次を追加する。

```yaml
status: superseded
superseded_by: ./new-design.md
```

単体リポジトリでの適用方針:

- 正本にのみ付与する。`.work/` の作業文書には不要。
- 大規模設計と ADR から始め、全 Markdown への必須化は段階的に判断する。

### 4.7 PR の文書影響欄

すべての PR で文書影響を宣言する。

```markdown
## Documentation impact

- [ ] 正本を更新した（設計書 / ADR / API / README / 運用手順 / トラブルシューティング）
- [ ] `.work/` の作業文書を蒸留し、削除した
- [ ] 文書更新は不要

理由:
```

文書に関するマージ条件:

- 設計と実装が矛盾していない。
- 未実装の設計に `implementation: planned` などの表示がある。
- 相対リンクが切れていない。
- 同じ情報を複数箇所で正本化していない。
- 実測していない手順を検証済みと断定していない。
- `.work/` が差分に残っていない。

## 5. マージ条件と `main` の保護

マージ条件:

- 対象ブランチが最新 `main` と競合していない。
- 必須テストと静的検査が成功している。
- 差分に秘密情報、生成物、不要ファイルが含まれていない。
- 正本の文書が更新されている、または不要と判断され理由が記載されている。
- `.work/` が削除されている。
- 破壊的変更、データ移行、設定変更の移行方法が記載されている。
- ロールバック方法が説明できる。

`main` の保護:

- force push を禁止する。
- 原則として直接 push を禁止する。
- Pull Request と必須チェックを要求する。
- CI が存在しない段階では、ローカル検証結果を PR に記録する。
- 個人開発でも PR を作り、セルフレビューの記録を残す。

---

## 6. 検証方針

検証コマンドはリポジトリの `CLAUDE.md`、README、CI 定義を正本とし、
本書には固定コマンドを重複記載しない。

最低限の検証カテゴリ:

| リポジトリ種別 | 検証 |
|---|---|
| アプリ・ライブラリ | format、lint、unit test、build |
| CLI ツール | 上記に加えて主要コマンドの実行確認 |
| 設定・dotfiles | 構文チェック、リンク・パス整合、実環境への適用確認 |
| 文書リポジトリ | Markdown リンク、文書メタデータ、見出し構造 |

実機確認が必要な項目は、CI 成功と区別して PR に記録する。

## 7. スキル化: `repo-branch`

目的: 単体リポジトリで作業ブランチを安全に開始し、コードと文書を
`main` マージ可能な状態まで整える。

配置は `claude/skills/repo-branch/`。

責務:

- 未コミット変更とブランチ状態を確認する。
- 変更目的からブランチ種別と名前を決める。
- 作業文書が必要な規模かを判定し、`.work/<topic>/` を用意する。
- 小規模変更か、設計先行（`design/`）が必要かを判定する。
- マージ前に蒸留を実行する（正本への反映 → PR 本文への要点転記 → `.work/` 削除）。
- リポジトリ固有の検証を実行する。
- diff、秘密情報、生成物、文書整合性を確認する。

非責務:

- 明示的な依頼なしに `main` へマージしない。
- タグを作成しない（`repo-release` の責務）。
- 既存のユーザーの未コミット変更を破棄しない。
- git の低レベル操作手順を再定義しない（下記）。

`git-ops` との境界:

| 観点 | 担当 |
|---|---|
| どのブランチを、いつ、どんな名前で作るか | `repo-branch` |
| 何を正本に書き、何を破棄するか | `repo-branch` |
| `git status` / diff 確認、コミットメッセージ生成、`gh` での PR 操作 | [`git-ops`](../claude/skills/git-ops/SKILL.md) |

`repo-branch` は判断（何を・いつ）を担い、実際の git 操作は `git-ops` に委譲する。
`git-ops` の内容を複製しない。

構成:

```text
repo-branch/
├── SKILL.md
└── references/
    └── documentation-policy.md   # 4章（正本と作業文書、蒸留判定表）
```

マイクロサービス版 `ms-branch` との関係:
`ms-branch` は本スキルを前提とした拡張であり、判断ロジックの共通部分は本書側を正本とする。
差分は「複数リポジトリ協調（`platform` 先行・契約変更）」に限る。
将来的に統合するかは 10 章の未決事項とする。

## 8. 導入順序

| 段階 | 内容 | 完了条件 |
|---|---|---|
| 1 | 本書の合意 | `status: accepted` へ変更 |
| 2 | `.work/` 運用の開始 | 1 件の変更で蒸留まで通す |
| 3 | PR テンプレート | 文書影響欄を利用開始 |
| 4 | PR 検証 CI | 最低限のチェックが自動実行される |
| 5 | `main` 保護 | PR とチェックを必須化 |
| 6 | `repo-branch` | 実案件で試行し、誤判定を修正 |

---

## 9. 運用指標

- `main` が壊れた回数と復旧時間。
- 蒸留漏れ（`.work/` が `main` にマージされた回数）。
- 正本の更新漏れが原因で手戻りした件数。
- `planned` のまま放置された設計数。
- 直接 push や検証省略など例外運用の回数。

運用負担に対して効果が薄いチェックは削減し、事故を防いだチェックは自動化する。

---

## 10. 未決事項

- `.work/` を全リポジトリ共通のディレクトリ名にするか、リポジトリごとに変えるか。
- 蒸留した作業文書を、削除ではなく別リポジトリ・別ブランチへ退避する運用を認めるか。
- `repo-branch` と `ms-branch` を 1 スキルに統合し、リポジトリ構成で分岐させるか。
- 文書メタデータを全 Markdown に必須化するか、大規模設計・ADR のみに限定するか。

初期推奨:

- `.work/` の名前は固定し、リポジトリ間で揃える。
- 退避は行わず削除する。必要な情報は PR 本文に残す。
- スキルは当面分けて運用し、重複が実運用で確認できてから統合を判断する。
