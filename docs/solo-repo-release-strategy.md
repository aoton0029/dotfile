# 単体リポジトリ リリース戦略 設計案

単一のリポジトリで完結する開発を対象に、**`main` マージ以降**（バージョン決定、
タグ発行、成果物公開、ロールバック）の運用モデルを定義する。

**本書はリリース運用の正本**である。SemVer 判定、タグ規約、CHANGELOG、
`implementation` の更新契機、ロールバック、ホットフィックスは本書で定義し、
他のリリース戦略文書はこれを参照・拡張する。

`main` へのマージまでは
[単体リポジトリ ブランチ戦略](solo-repo-branch-strategy.md) を参照する。

複数リポジトリを協調させるリリースは、本書を前提に差分のみを定義した
[マイクロサービス リリース戦略](microservice-release-strategy.md) を参照する。

```yaml
status: proposed
implementation: planned
last_reviewed: 2026-08-17
```

---

## 1. 目的

- 「どのコミットが、どのバージョンとして世に出たか」を後から特定できるようにする。
- 利用者に対する互換性の約束を明示する。
- 壊れたときに戻す手段を、リリース前に用意しておく。
- タグを打たないリポジトリにも、無理のない扱いを与える。

対象外:

- ブランチ運用、PR 条件、文書の蒸留（ブランチ戦略の責務）。
- 複数リポジトリのバージョン組み合わせ管理。

---

## 2. リリースの定義

単体リポジトリでは 2 段階を区別する。

| 段階 | 完了条件 | 責務 |
|---|---|---|
| コード統合 | `main` にマージ済み | ブランチ戦略 |
| リリース | `main` の特定コミットにタグを打ち、成果物を確定した | 本書 |

「`main` に入った」と「リリースした」を同じ意味で使わない。
タグを打った時点の `main` が、そのバージョンの正本となる。

成果物の実体はリポジトリ種別で異なる（パッケージ、実行ファイル、
コンテナイメージ、GitHub Release の添付物、あるいは「タグのみ」）。
本書はどれであっても手順を共通に扱う。

---

## 3. 通常リリース手順

1. `main` が最新で、CI が正常であることを確認する。
2. 前回タグ以降の変更を確認する（`git log <前回タグ>..main`）。
3. 変更内容から SemVer を決定する（4 章）。
4. CHANGELOG を更新し、`main` へマージする（5 章）。
5. `vX.Y.Z` の annotated tag を作成する。
6. タグを push し、成果物の発行完了を確認する。
7. 成果物の取得・実行を 1 回確認する。
8. 設計書の `implementation` を更新する（5 章）。
9. リリース結果と既知の問題を記録する。

原則:

- タグは常に `main` のコミットに打つ。作業ブランチには打たない。
- 一度 push したタグを付け替え・削除しない。誤りは次のバージョンで直す。
- annotated tag（`git tag -a`）を使い、軽量タグを使わない。

---

## 4. SemVer

| 変更 | バージョン |
|---|---|
| 後方互換な不具合修正、軽微な修正 | PATCH |
| 後方互換な機能追加 | MINOR |
| 既存の利用方法・API・データに破壊的変更 | MAJOR |

- `0.y.z` の期間でも、破壊的変更は最低でも MINOR を上げ、リリースノートに明記する。
- 成果物を伴わない文書のみの変更には、原則としてタグを付けない。

### 4.1 「破壊的変更」の意味はリポジトリ種別で異なる

同じ基準を機械的に当てず、そのリポジトリで**外部との接点は何か**を先に定める。

| リポジトリ種別 | 外部との接点 | 破壊的変更の例 |
|---|---|---|
| ライブラリ | 公開 API、型定義 | 公開関数の削除・シグネチャ変更、例外仕様の変更 |
| CLI ツール | コマンド、オプション、出力形式、終了コード | オプション削除、出力フォーマット変更、終了コードの意味変更 |
| アプリケーション | 設定ファイル、環境変数、データ形式、保存データ | 設定キーの削除、非互換なデータ移行、既定動作の変更 |
| 設定・dotfiles | 前提とする環境、リンク先パス | 既存環境で再適用すると壊れる変更（7 章も参照） |

内部実装の変更は、外部との接点が変わらない限り破壊的変更として扱わない。

---

## 5. リリースに伴う文書更新

### 5.1 CHANGELOG

- 生成元は `main` の squash コミットメッセージ（Conventional Commits）とする。
- 自動生成した内容をそのまま出さず、利用者視点で読める文言に整える。
- 破壊的変更は独立した見出しで示し、移行方法を書く。
- CHANGELOG はリリース時に更新し、タグはその更新後のコミットに打つ。

### 5.2 設計書の状態更新

`status` / `implementation` の定義は
[単体リポジトリ ブランチ戦略 4.6](solo-repo-branch-strategy.md) を正本とする。
本書は更新契機のみを扱う。

| 契機 | 更新内容 |
|---|---|
| 設計に対応する実装がすべて `main` に入った | `implementation: implemented` へ更新 |
| 一部のみ反映した | `partially-implemented` とし、残りを書く |
| リリースした | リリース記録にタグと確認結果を残す |

リリース前に、`implementation: planned` のまま実装済みになっている設計書がないか確認する。

---

## 6. ロールバックとホットフィックス

### 6.1 ロールバック

- 利用者側は直前の既知正常版のタグへ戻す。
- 以前のタグを上書きしない。成果物を差し替えない。
- 誤って公開したバージョンは、取り下げるのではなく**修正版を出す**ことを基本とする。
  公開を取り下げる場合は、依存している利用者への影響を先に確認する。
- 設定・データ変更は `git revert` または前バージョンへの明示的な変更 PR で戻す。
- データ移行を伴う変更は、後方互換な段階移行（expand/contract）を優先する。
- ロールバック不能な変更は、リリース前にその理由と復旧方法を承認しておく。

### 6.2 ホットフィックス

1. 最新 `main` から `hotfix/<topic>` を作る。
2. 障害範囲に限定した最小修正を行う。
3. 省略できない安全確認を実行する。
4. PR 経由で `main` へマージする。
5. PATCH タグを発行する。
6. 原因と恒久対策をトラブルシューティングまたは ADR に残す。

緊急性は、秘密情報検査、バックアップ判断、ロールバック準備を省略する理由にならない。
`.work/` の蒸留も省略しない（規模が小さければ作業文書自体が不要）。

---

## 7. バージョンを持たないリポジトリ

dotfiles や個人の設定リポジトリのように、成果物を発行せず、
利用者が常に `main` を追う種類のリポジトリがある。

このようなリポジトリでは:

- **リリース = `main` へのマージ**と定義する。
- 本書 3〜6 章は適用しない。タグ・CHANGELOG・SemVer を導入しない。
- 代わりに、次を守る。
  - 既存環境で再適用したときに壊れる変更は、README または移行メモに明記する。
  - 破壊的な変更は、変更前の状態へ戻す手順を PR 本文に書く。
  - 適用は各環境で明示的な操作（pull と再リンク）として行い、自動追従させない。

判断基準: **他人または他の環境が特定バージョンに固定して依存するか**。
依存するならタグを打つ。常に最新を追うだけならタグは不要。

---

## 8. 検証方針

検証コマンドはリポジトリの `CLAUDE.md`、README、CI 定義を正本とし、
本書には固定コマンドを重複記載しない。

| 対象 | 検証 |
|---|---|
| タグ時点のコード | CI 成功、`main` との一致 |
| 成果物 | 発行完了、取得できること、1 回の実行確認 |
| 文書 | CHANGELOG の記載、`implementation` の更新、リンク切れ |

実機確認が必要な項目は CI 成功と明確に区別して記録する。

---

## 9. スキル化: `repo-release`

目的: 単体リポジトリで、`main` の状態からリリース可否を判断し、
バージョン決定からタグ発行・記録までを安全に進める。

配置は `claude/skills/repo-release/`。

責務:

- リリース対象リポジトリがタグを打つ種別かを判定する（7 章）。
- 前回タグ以降の変更を収集し、SemVer を提案する（4 章、種別ごとの接点定義を含む）。
- CHANGELOG の草案を作る。
- 設計書の `implementation` 更新漏れを検出する。
- リリース前チェック（`main` 最新、CI 成功、未コミット変更なし、秘密情報なし）を行う。
- タグ発行と成果物確認を、ユーザー確認の上で実行する。
- リリース記録を残す。

非責務:

- 確認なしにタグを push しない。
- 既存タグを付け替え・削除しない。
- ブランチを作らない、`main` へマージしない（`repo-branch` の責務）。
- git の低レベル操作手順を再定義しない。

`git-ops` との境界:

| 観点 | 担当 |
|---|---|
| リリースするか、どのバージョンにするか | `repo-release` |
| 何を CHANGELOG と記録に残すか | `repo-release` |
| `git log` / status 確認、コミット、push、`gh release` 操作 | [`git-ops`](../claude/skills/git-ops/SKILL.md) |

構成:

```text
repo-release/
├── SKILL.md
└── references/
    └── versioning.md   # 4章（SemVer とリポジトリ種別ごとの接点定義）
```

マイクロサービス版 `ms-release` との関係:
`ms-release` は本スキルを前提とした拡張であり、SemVer 判定・タグ規約・CHANGELOG の
ロジックは本書側を正本とする。差分は「デプロイ構成更新と本番反映」および
「複数サービスの組み合わせ管理」にある。統合可否は 12 章の未決事項とする。

---

## 10. 導入順序

| 段階 | 内容 | 完了条件 |
|---|---|---|
| 1 | 本書の合意 | `status: accepted` へ変更 |
| 2 | リポジトリ種別の判定 | タグを打つ / 打たないを明文化 |
| 3 | CHANGELOG の開始 | 1 回のリリースで運用を通す |
| 4 | タグ運用 | `vX.Y.Z` の annotated tag を発行 |
| 5 | リリース CI | タグ push で検証と成果物発行が走る |
| 6 | `repo-release` | 実案件で試行し、誤判定を修正 |

---

## 11. 運用指標

- リリース後に判明した不具合の件数と、修正までの時間。
- SemVer の判定誤り（破壊的変更を MINOR 以下で出した回数）。
- CHANGELOG の記載漏れ。
- `planned` のまま残っていた設計書の数。
- タグの付け替え・削除を行った回数（0 を維持する）。

---

## 12. 未決事項

- CHANGELOG を手書きするか、Conventional Commits からの自動生成に寄せるか。
- リリース記録を CHANGELOG に集約するか、GitHub Release 本文に持たせるか。
- `repo-release` と `ms-release` を 1 スキルに統合するか。
- プレリリース版（`-rc.1` など）を運用に含めるか。

初期推奨:

- CHANGELOG は自動生成を下書きとし、公開前に人が整える。
- リリース記録は GitHub Release 本文に置き、CHANGELOG は利用者向けに簡潔に保つ。
- プレリリースは当面導入せず、必要になった時点で追加する。
