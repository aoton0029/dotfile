# マイクロサービス ブランチ戦略 設計案

複数のサービスリポジトリと `platform` リポジトリ、およびそれらを固定バージョンで
組み合わせるデプロイ構成リポジトリを対象に、**作業ブランチの開始から `main` への
マージ準備までの一貫した運用モデル**を定義する。

**本書は [単体リポジトリ ブランチ戦略](solo-repo-branch-strategy.md) を正本とし、
それを複数リポジトリ協調のために拡張する差分文書である。**
ブランチ種別・命名規則・作業サイクル・文書メタデータ・文書種別の責務・
蒸留・設計 PR の必須項目・`main` の保護は正本側で定義済みであり、本書では再定義しない。
本書が扱うのは次の 3 点に限る。

1. 複数リポジトリの役割分担と、リポジトリ間の正本配置。
2. サービス間契約が変わる変更の進め方（`platform` 先行）。
3. リポジトリ種別ごとの検証とマージ条件の追加分。

正本と矛盾する記述が生じた場合は、正本側を優先し本書を修正する。

`main` マージ以降（タグ発行・成果物リリース・本番反映）は
[マイクロサービス リリース戦略](microservice-release-strategy.md) を参照する。

```yaml
status: proposed
implementation: planned
last_reviewed: 2026-08-17
extends: ./solo-repo-branch-strategy.md
supersedes: ./development-design-release-strategy.md
```

---

## 1. 目的

正本の目的（`main` を説明可能に保つ、コードと文書の乖離を防ぐ、
人間と AI エージェントが同じチェックポイントに従う）に加えて:

- 複数リポジトリにまたがる変更でも、どこが正本かを一意に決められるようにする。
- サービス間契約の変更を、部分適用状態を作らずに進める。

対象外（正本の対象外に加えて）:

- 秘密情報や実環境固有値の Git 管理。
- タグ発行、成果物リリース、本番反映（リリース戦略側の責務）。

---

## 2. 前提となるリポジトリモデル（正本）

リポジトリを役割で分類する。正本（単体リポジトリ戦略）は「1 リポジトリ」を前提とするため、
この分類が本書の拡張の起点になる。マイクロサービス系文書における
**リポジトリモデルの正本は本節**とし、リリース戦略側では複製せず本節を参照する。

| 種別 | 役割 | `main` の意味 |
|---|---|---|
| サービス（アプリケーション） | ソースコード、テスト、サービス固有設計 | リリース可能なコードと文書 |
| `platform` | 横断設計、サービス間契約、横断ユースケース | 承認されたシステム仕様の正本 |
| デプロイ構成 | Compose、固定イメージタグ、サービス間接続 | 本番で採用する望ましい構成 |
| システム設計・運用 | 実環境の構成、運用、ランブック | 承認された運用手順の正本 |

`platform` リポジトリの位置づけと標準構成は
[マイクロサービス開発用スキル群 設計案](microservice-skills-design.md) を正本とする。

代表的な関係:

```mermaid
flowchart LR
    A[サービス main] --> B[vX.Y.Z タグ]
    B --> C[固定タグのコンテナイメージ]
    C --> D[デプロイ構成のタグ更新]
    D --> E[デプロイ構成 main]
    E --> F[本番への手動反映]
```

サービスの `main` マージは、直ちに本番稼働を意味しない。
**本ドキュメントの責務は図の左端（`main` マージまで）に閉じる。**

## 3. ブランチ戦略（差分）

### 3.1 正本から引き継ぐもの

ブランチモデル（常設は `main` のみ、短命な作業ブランチ、squash merge）、
ブランチ種別と命名規則、作業開始・作業中の手順、`main` の保護は
[単体リポジトリ ブランチ戦略 2 章・3 章・5 章](solo-repo-branch-strategy.md) に従う。

複数リポジトリ運用で追加される点だけを以下に定義する。

### 3.2 作業開始時の追加手順

作業開始の前に、**対象リポジトリと変更範囲を確定する**。

- 変更がサービス内部に閉じるか、サービス間契約に触れるかを先に判定する。
- 契約に触れる場合は 3.3 に従い、`platform` の変更から始める。
- 変更に関与するリポジトリを列挙し、それぞれで作業ブランチが必要かを判断する。

### 3.3 サービスをまたぐ変更のブランチ

サービス間契約が変わる変更では、`platform` を先に変更する（spec-first）。

```text
platform: design/<topic>       ← 契約・横断設計をマージ
  → service-a: feat/<topic>
  → service-b: feat/<topic>
  → deploy:    chore/<topic>   ← 固定タグ更新はリリース戦略側
```

- 各リポジトリのブランチ名は同じ `<topic>` に揃え、PR 本文で相互リンクする。
- 実装 PR の本文に、前提となる `platform` PR を必ず記載する。
- 契約に反する実装を、`platform` を後追いで直す前提でマージしない。

### 3.4 マージ条件の追加分

正本 5 章のマージ条件に、次を追加する。

- サービスをまたぐ場合、前提となる `platform` の変更がマージ済みである。
- 契約変更を含む場合、消費側サービスへの移行方法が PR に記載されている。
- デプロイ構成に影響する変更は、影響する構成ファイルと更新順序が示されている。

## 4. 設計ドキュメント戦略（差分）

### 4.1 正本から引き継ぐもの

文書メタデータ（`status` / `implementation` / `last_reviewed`）、
正本と作業文書の分離、`.work/` の運用と蒸留、文書種別と責務、
設計 PR の必須項目、PR の文書影響欄は
[単体リポジトリ ブランチ戦略 4 章](solo-repo-branch-strategy.md) に従う。

### 4.2 文書種別の追加

正本の文書種別表に、複数リポジトリ運用で次を追加する。

| 文書 | 答える問い | 更新契機 | 置き場所 |
|---|---|---|---|
| システム設計 | システム全体をどう分割・接続するか | 横断設計変更 | `platform` |
| サービス設計 | サービス内部をどう実現するか | 内部設計変更 | サービス |
| サービス間契約 | サービス境界で何を約束するか | I/F 変更 | `platform` |

正本の「API・契約」は、マイクロサービスでは
「サービス間契約（`platform`）」と「公開ポート・環境変数インターフェース
（デプロイ構成）」に分かれる。どちらに書くかは 4.4 の表で決める。

設計書に書いてよいこと・書いてはいけないことは
[`ms-design-rules`](microservice-skills-design.md) を正本とする。

### 4.3 設計先行が必要になる追加条件

正本の設計先行条件に、次を追加する。

- 複数リポジトリまたは複数サービスにまたがる。
- サービス間契約またはデータ所有権が変わる。
- ネットワーク、認証、ストレージ構成が変わる。
- 新しいサービスや外部依存を導入する。

これらに該当する場合、設計 PR は原則として `platform` の `design/<topic>` で行う。

### 4.4 リポジトリ間の正本

| 情報 | 正本を置く場所 |
|---|---|
| システム全体の目的・境界 | `platform` |
| サービス間契約・横断ユースケース | `platform` |
| ネットワーク、DNS、TLS、ストレージ | システム設計・運用リポジトリ |
| 実環境の構築・バックアップ・災害復旧 | システム設計・運用リポジトリ |
| Compose と固定イメージタグ | デプロイ構成リポジトリ |
| サービスの公開ポート・環境変数インターフェース | デプロイ構成リポジトリ |
| サービス固有の PRD・API・データモデル・UI | サービスリポジトリ |
| サービス内部の技術決定 | サービスリポジトリの ADR |

他のリポジトリには情報を複製せず、正本へ相対リンクまたはリポジトリ URL で参照する。
要約が必要な場合も、どちらが正本かを明記する。

### 4.5 設計 PR の必須項目（追加分）

正本の必須項目に、次を追加する。

- 影響するリポジトリとサービスの一覧。
- サービス間契約の変更点と、後方互換性の有無。
- 非互換な場合の段階移行（expand/contract）計画とリリース分割。
- 関連する各リポジトリの PR への相互リンク。

### 4.6 PR の文書影響欄（追加分）

正本のチェック項目に、次を追加する。

```markdown
- [ ] システム設計（platform）
- [ ] サービス間契約（platform）
- [ ] デプロイ構成（公開ポート・環境変数）
```

文書に関するマージ条件の追加分:

- 他リポジトリの正本を複製せず、参照になっている。
- 契約変更が `platform` 側の正本に反映済みである。

## 5. マージ前の検証方針（差分）

検証コマンドを本書に重複記載しない方針は正本 6 章に従う。
リポジトリ種別が増えるため、検証カテゴリのみ本書で定義する。

| リポジトリ種別 | 検証 |
|---|---|
| サービス | format、lint、unit test、build、契約テスト、必要な integration test |
| `platform` | Markdown リンク、契約定義の妥当性、設計書メタデータ |
| デプロイ構成 | Compose 展開、必須変数、固定タグ、ポート・volume 競合 |
| システム設計・運用 | Markdown リンク、スクリプト構文、手順間の整合性 |

実機確認が必要な項目は CI 成功と区別する（リリース戦略側のチェックリストで扱う）。

## 6. スキル化: `ms-branch`

目的: `repo-branch` の判断に、複数リポジトリ協調の判定を上乗せする。

配置は `claude/skills/` 配下。命名接頭辞 `ms-` はスキル群設計案に合わせる。

`repo-branch` との関係:
`ms-branch` は [`repo-branch`](solo-repo-branch-strategy.md) を前提とし、
ブランチ命名・`.work/` 運用・蒸留・PR 準備の判断ロジックを再定義しない。
SKILL.md に「`repo-branch` の規範に従うこと」を明記し、本書の差分のみを持つ。

固有の責務:

- 対象リポジトリ種別と適用ルールを特定する（`ms-context` を先に呼ぶ）。
- 変更がサービス間契約に触れるかを判定する。
- サービスをまたぐ変更で `platform` 先行が必要かを判定する。
- 文書の正本がどのリポジトリにあるかを 4.4 の表から選ぶ。
- リポジトリ横断の PR 相互リンクが揃っているか確認する。
- リポジトリ種別ごとの検証（5 章）を行う。

非責務:

- 明示的な依頼なしに `main` へマージしない。
- タグを作成しない（`ms-release` の責務）。
- 本番へデプロイしない。
- 既存のユーザー変更を破棄しない。

構成:

```text
ms-branch/
├── SKILL.md                       # repo-branch を前提として宣言
└── references/
    ├── cross-repo-policy.md       # 第2章・第3章・第4.4節
    └── contract-change-policy.md  # 第3.3節・第4.3節・第4.5節
```

`repo-branch/references/documentation-policy.md` を複製しない。

`ms-release` との関係、および共通規範スキルの扱いは
[リリース戦略 第6章](microservice-release-strategy.md) を参照する。

## 7. 導入順序

正本の導入順序を各リポジトリで先に通し、その上で本書の差分を積む。

| 段階 | 内容 | 完了条件 |
|---|---|---|
| 0 | 正本（単体リポジトリ ブランチ戦略）の適用 | 各リポジトリ単体で運用が回る |
| 1 | 本書の合意 | `status: accepted` へ変更 |
| 2 | リポジトリ間の正本表（4.4）の確定 | 各情報の置き場所が一意に決まる |
| 3 | PR テンプレートへの差分項目追加 | 契約変更欄を利用開始 |
| 4 | PR 検証 CI | リポジトリごとの最低限チェックが自動実行される |
| 5 | `main` 保護 | 全リポジトリで PR とチェックを必須化 |
| 6 | `ms-branch` | 実案件で試行し、誤判定を修正 |

---

## 8. 運用指標

- `main` が壊れた回数と復旧時間。
- 文書不足が原因で手戻りした件数。
- `planned` のまま放置された設計数。
- 直接 push や検証省略など例外運用の回数。
- スキルが誤ったリポジトリまたは文書を正本と判断した回数。

運用負担に対して効果が薄いチェックは削減し、事故を防いだチェックは自動化する。

---

## 9. 未決事項

正本側の未決事項（文書メタデータの必須化範囲、`.work/` の扱い、スキル統合）は
本書で重複して扱わない。本書固有の未決事項は次のとおり。

- サービスをまたぐ変更で、リポジトリ横断の PR 進捗をどこで追跡するか
  （`platform` の設計書には進行表を書かない方針との整合）。
- `.work/` を各リポジトリに持つか、`platform` に横断トピックとして集約するか。
- 正本（単体リポジトリ戦略）そのものを各リポジトリへどう配布するか
  （dotfiles からのリンクか、リポジトリごとの複製か）。
- 共通スキルをユーザースコープへ置くか、リポジトリスコープへ置くか。

初期推奨:

- 横断 PR の進捗は `platform` の設計 PR 本文で追跡し、マージ時に破棄する。
- `.work/` は変更が発生する各リポジトリに置き、`<topic>` を揃える。
- 正本は複製せず、dotfiles 管理の 1 か所を参照する。
- スキルはリポジトリで版管理し、`claude/skills` のリンク経由で利用する。
